## 1. What it is

A small sales model — customers, orders, order lines — chosen to exercise the
decisions most likely to be wrong in practice rather than to be realistic. It is
30 items across three Contexts, and every structural feature the specification
argues about appears exactly once.

`[CORRECTED]` It *was* generated by a `build_example.py`, which is no longer in
the repository — `make dist` still called it and swallowed the failure, so the
example has in fact been maintained as a file for some time. What keeps it
honest now is not the generator but the two checks that always ran beside it:
the round trip is byte-identical, and `make model` reports exactly the three
findings it is designed to carry.

The original reason for generating it was
that matters: **the built-in validator UUIDs are computed, not invented.** They
come from the real scheme in spec §5.7 —

```python
NAMESPACE_STDLIB = uuid5(NAMESPACE_DNS, "stdlib.designer")
builtin_uuid     = uuid5(NAMESPACE_STDLIB, canonical_name)
```

so `max_length` really is `b5bfc6ca-adeb-523c-8b84-ec070bb68290` on every machine
that implements the scheme. A hand-written placeholder would have proved nothing
and would have had to be replaced later.

## 2. The shape of the model

```
common/                                sales/
  Uuid, ShortText, CountryCode,          OrderNumber          (Type)
  Money, PositiveMoney, Weight           is_order_number      (leaf Validator)
  id, name, country_code,                order_reference      (composite Validator)
  created_at, amount                     order_number, quantity
  Auditable          (abstract)          LineItem   (abstract, extends Auditable)
  Customer           (extends Auditable) Order      (extends Auditable)
                                         OrderLine  (extends LineItem)
                                         sales_schema
```

`Customer` lives in `common` deliberately. It is the shared-entity case from
spec §9.1 — visible to every Schema below, a member of whichever ones list it.

## 3. What each feature is there to prove

| Feature | Where | Why it is in the example |
|---|---|---|
| **Nullable reference** | `Weight` has `parent: null` | The whole §3.1 argument. An unfinished item must load, save and report as `incomplete` rather than fail. |
| **Type chain and narrowing** | `PositiveMoney` → `Money` → `decimal` | The chain walk §6 depends on, and the thing the slot override is checked against. |
| **Slot narrowing** | `OrderLine.line_total` overrides `LineItem.line_total` | Type narrowed `Money` → `PositiveMoney`, `required` false → true. The §8.1 rule and the reason flattened materialization was chosen. |
| **Abstract entity** | `Auditable`, `LineItem` | Factoring shared slots; never a table; never a Schema member; not a reference target. |
| **Inherited identity** | `LineItem` declares it, `OrderLine` inherits | §8.1's "declared at the root, inherited below". |
| **`slot_name` override** | `Order.ship_to_country` uses property `country_code` | Proves the slot name and the property name are separate, which is what lets one Entity hold two slots over the same Property. |
| **Reference slots** | `Order.customer`, `OrderLine.order` | `inverse_name`, and both `restrict` and `cascade` `on_delete`. |
| **Composite operands as UUIDs** | `order_reference` = `<is_order_number> OR <is_uuid>` | §5.2's stored form. Open the JSON and it is unreadable without substitution — which is the point, and why the JSON tab shows the stored form (§12). |
| **Binding UUIDs** | every binding | The §3 locator decision from the diagnostics appendix, in its first real use. |
| **Per-binding message override** | `ShortText`'s `max_length` | "must be 80 characters or fewer" instead of the library's wording. |
| **Typed literal envelope** | `{"literal": {"decimal": "0.00"}}` | §4.1's insistence that a decimal is a string, never a JSON number. |
| **Non-deterministic binding** | `Auditable` binds `in_past` | Produces the warning that no CHECK constraint can carry it (§5.7). |
| **Schema membership** | `sales_schema` lists three entities | Explicit, non-exclusive, curated (§9.1). Note `Auditable` and `LineItem` are absent — abstract entities are never members. |
| **Closure** | Order → Customer, OrderLine → Order, both members | The schema is closed. Remove `Customer` and it stops being. |
| **Anchored path** | `order.customer.country_code` | Three segments, ends on a value slot, every entity a member (§9.3). Stored as slot UUIDs, not a dotted string (§12). |

## 4. Expected findings

Run against a correct implementation, the document produces **exactly three
findings and no errors**:

```
warning     MOD602  Auditable binds a non-deterministic validator; no CHECK constraint
incomplete  MOD101  Type Weight has no parent
info        MOD601  Type Weight is referenced by nothing
```

All three are deliberate. Together they make the example a fixture with a known
answer at all four severities that matter, rather than a document that merely
loads.

## 5. The checker

`tools/check_model.py` verifies the structural rules — references resolve, chains
reach a BaseType, narrowing narrows, abstract entities are not targeted or
enrolled, schemas are closed, paths are well-formed and stay inside membership,
names are unique per Context and kind. It does not type-check expressions; that
is the signature table's job and belongs in the real implementation.

It is throwaway in one sense and not in another. As code it will be replaced by
`designer-model`'s model check. As a **specification of expected behaviour** it
is worth keeping, because it was written against the documents rather than
against an implementation, and it already disagrees with nothing.

Four deliberately broken variants confirm it has teeth:

| Mutation | Findings |
|---|---|
| `OrderLine` widens the inherited `line_total` | `MOD412` required true→false, `MOD413` widens rather than narrows |
| `Customer` removed from `sales_schema` | `MOD503` schema not closed, `MOD509` path leaves the schema |
| `OrderLine.order` retargeted at abstract `LineItem` | `MOD401` targets abstract, `MOD503`, plus the path failures that follow |
| A value slot appended to the middle of a path | `MOD508` path traverses a value slot |

The second is worth dwelling on: removing one member produced both a closure
warning *and* a path error, from two rules that never reference each other. That
is the §9.2 and §9.3 interaction behaving as designed — closure-on-add exists
precisely so the path rule is rarely the thing that fires.

## 6. What it does not cover

Honest gaps, none of which need closing before phase 1:

- **No expression type-checking.** The bindings are structurally valid; nothing
  here proves `max_length(80)` type-checks against a `string`. That needs the
  signature table implemented, and the standard library's own example values are
  the better fixture for it.
- **No `one_of` list argument**, no `duration` arithmetic, no `time` slot. The
  library's self-test covers these more directly than a model document would.
- **One Schema.** The shared-entity case is set up — `Customer` sits in `common`
  — but a second Schema also listing it would be needed to demonstrate
  non-exclusive membership actually working.
- **Deep paths.** The longest path is three segments; nothing here reaches the
  four-segment limit or crosses it.

Adding a second Schema is the one worth doing early, since non-exclusive
membership is the decision that was reversed most often during design and is
therefore the one most likely to have left a loose end.
