# Designer — Worked Example

29 August 2026, corrected 30 August, brought up to date 17 October. Companion to
`examples/sales.json`, its sisters `examples/sales_interfaces.json` and
`examples/sales_broken.json`, the export files beside them, and
`tools/check_model.py`.

`[CORRECTED]` The two original files were called `designer-example-sales.json`
and `designer-check.py` when this was written, before the repository had a shape.

---

## 1. What it is

A small sales and support model — customers, orders, order lines, tickets —
chosen to exercise the decisions most likely to be wrong in practice rather than
to be realistic. It is 30 items across three Contexts.

`[CORRECTED]` It *was* generated by a `build_example.py`, which is no longer in
the repository. The example is maintained as a file, and what keeps it honest is
the checks that run beside it: the round trip is byte-identical, it carries
exactly three findings (§4), and the export of each Schema is compared byte for
byte with a committed file (§7).

The original reason for generating it still matters: **the built-in validator
UUIDs are computed, not invented.** They come from the real scheme in spec §5.7 —

```python
NAMESPACE_STDLIB = uuid5(NAMESPACE_DNS, "stdlib.designer")
builtin_uuid     = uuid5(NAMESPACE_STDLIB, canonical_name)
```

so `max_length` really is `b5bfc6ca-adeb-523c-8b84-ec070bb68290` on every machine
that implements the scheme.

## 2. The shape of the model

```
common/                              sales/  (under common)          support/  (under common)
  Uuid, ShortText, CountryCode,        OrderNumber        (Type)       Priority     (Type)
  Money, PositiveMoney, Weight         is_order_number    (leaf)       subject, priority
  id, name, country_code,              order_reference    (composite)  Ticket       (extends Auditable)
  created_at, amount                   order_number, quantity          support_schema
  Auditable   (abstract)               LineItem   (abstract, extends Auditable)
  Customer    (extends Auditable)      Order      (extends Auditable)
                                       OrderLine  (extends LineItem)
                                       sales_schema
```

`Customer` lives in `common` deliberately. It is the shared-entity case from
spec §9.1 — visible to every Schema below, and a member of both `sales_schema`
and `support_schema`. `sales` and `support` are siblings: neither can see the
other.

## 3. What each feature is there to prove

| Feature | Where | Why it is in the example |
|---|---|---|
| **Nullable reference** | `Weight` has `parent: null` | The whole §3.1 argument. An unfinished item must load, save and report as `incomplete` rather than fail. |
| **Type chain and narrowing** | `PositiveMoney` → `Money` → `decimal` | The chain walk §6 depends on, and the thing the slot override is checked against. |
| **Slot narrowing** | `OrderLine.line_total` overrides `LineItem.line_total` | Type narrowed `Money` → `PositiveMoney`, `required` false → true. The §8.1 rule and the reason flattened materialization was chosen. |
| **Abstract entity** | `Auditable`, `LineItem` | Factoring shared slots; never a table; never a Schema member; not a reference target. |
| **Inherited identity** | `LineItem` declares it, `OrderLine` inherits | §8.1's "declared at the root, inherited below". |
| **`slot_name` override** | `Order.ship_to_country` uses property `country_code` | Proves the slot name and the property name are separate, which is what lets one Entity hold two slots over the same Property. |
| **Reference slots** | `Order.customer`, `OrderLine.order`, `Ticket.customer` | `inverse_name`, and both `restrict` and `cascade` `on_delete`. `Ticket.customer` reaches `common` from `support`. |
| **Composite operands as UUIDs** | `order_reference` = `<is_order_number> OR <is_uuid>` | §5.2's stored form. Open the JSON and it is unreadable without substitution — which is the point. |
| **Binding UUIDs** | every binding | The locator decision from the diagnostics appendix §3, in its first real use. |
| **Per-binding message override** | `ShortText`'s `max_length` | "must be 80 characters or fewer" instead of the library's wording. |
| **Typed literal envelope** | `{"literal": {"decimal": "0.00"}}` | §4.1's insistence that a decimal is a string, never a JSON number. |
| **List literal argument** | `Priority` binds `one_of` over `["low", "normal", "high", "urgent"]` | §5.6's list literal, and a string default (`"normal"`) on `Ticket.priority`. |
| **Non-deterministic binding** | `Auditable` binds `in_past` | Produces the warning that no CHECK constraint can carry it (§5.7). |
| **Schema membership** | `sales_schema` lists three entities, `support_schema` two | Explicit, non-exclusive, curated (§9.1). `Auditable` and `LineItem` are absent — abstract entities are never members. |
| **Closure** | Order → Customer, OrderLine → Order, Ticket → Customer | Both schemas are closed. Remove `Customer` from either and it stops being. |
| **Anchored path** | `order.customer.country_code` | Three segments, ends on a value slot, every entity a member (§9.3). Stored as slot UUIDs, not a dotted string (§12). |
| **Indexes** | `Customer.name`, unique `Order.order_number`, two-slot `Ticket(customer, priority)` | Single, unique and composite indexes, as the export writes them. |

## 4. Expected findings

The document produces **exactly three findings and no errors**. `make model`
shows the warning and says two more are below its default level;
`tools/check_model.py examples/sales.json --level everything` shows all three:

```
warning     MOD602   Entity.validators[b0000000]
                     Auditable (e0000000) binds in_past (2754a6b3), which is not deterministic; no check constraint can enforce it
incomplete  MOD101   Type.parent
                     Type Weight (d0000000) has no parent yet
note        MOD601   Type
                     Weight (d0000000) is referenced by nothing
```

(*note* is how the tool shows severity `info`.) All three are deliberate:
together they make the example a fixture with a known answer at the severities
that matter, rather than a document that merely loads. `MOD101` blocks an
export, but only of a Schema that reaches `Weight` — and none does, which is
what lets both Schemas export (§7).

## 5. The checker, and four mutations

`tools/check_model.py` is a thin command-line front to `designer-model`'s model
check (`designer_model.check.Checker`): every structural rule, the expression
type checker (the `EXP` codes), the Interface checks (`INT`), and the standard
library. It also verifies the round trip before reporting, since a document that
does not survive one would make every finding about the wrong model.

Mutations confirm it has teeth (`test_check.py` pins the codes):

| Mutation | Findings beyond the three |
|---|---|
| `OrderLine.line_total` overridden with `ShortText` instead of `PositiveMoney` | `MOD413` — the override does not narrow `Money` |
| `LineItem.line_total` made required, `OrderLine.line_total` made optional | `MOD412` — an override may not relax `required` |
| `Customer` removed from `sales_schema` | `MOD503` schema not closed, `MOD509` path leaves the schema |
| `OrderLine.order` retargeted at abstract `LineItem` | `MOD401` targets abstract, `MOD404` a target with descendants, `MOD503`, and the path failures that follow (`MOD506`, `MOD509`) |
| A value slot put in the middle of the path | `MOD508` path traverses a value slot |

`[CORRECTED]` The first row used to read "`OrderLine` widens the inherited
`line_total` → `MOD412`, `MOD413`". That cannot happen in this model: the
inherited slot is optional, so there is no `required` to relax. It takes the two
separate mutations above.

The third is worth dwelling on: removing one member produced both a closure
warning *and* a path error, from two rules that never reference each other. That
is the §9.2 and §9.3 interaction behaving as designed — closure-on-add exists
precisely so the path rule is rarely the thing that fires.

## 6. What it does not cover

- **No Interfaces.** It is a `schema_version` 1 document on purpose — that is
  what proves a model without Interfaces stays at version 1 and round-trips byte
  for byte. `sales_interfaces.json` (§8) is the version 2 sister.
- **No `duration` arithmetic, no `time` slot.** The library's own examples
  (`data/examples.json`, validator library §9) cover the built-ins more directly
  than a model document would.
- **Deep paths.** The longest path is three segments; nothing reaches the
  four-segment limit or crosses it.
- **Composites beyond `OR`**, a reference slot inside an identity, and
  `enforcement: "database"` (`MOD603`) appear in tests but in no example file.

## 7. The exports

Each Schema's export is committed beside the model and regenerated by nothing —
the tests compare the exporter's output with them byte for byte:

| File | From | What it shows |
|---|---|---|
| `sales_schema.export.json` | `sales.json` | Resolved rules along the Type chain, expanded composites, `numeric` and `length` hints, `<slot>_<key>` reference columns (`customer_id`, `order_order_number`), application rules, the cross-table rule. |
| `support_schema.export.json` | `sales.json` | A second Schema sharing `Customer`; the `one_of` check with its list; a two-column index; a string default. |
| `sales_interfaces.export.json` | `sales_interfaces.json` | Real `interface` blocks (appendix *interfaces* §8): separators on numeric columns only, an inherited Interface exported as though declared. |

## 8. `sales_interfaces.json`

The same model at `schema_version` 2, with eight Interfaces and three new Types
to carry them:

| Interface | Picture | Bound to | Shows |
|---|---|---|---|
| `money_uk` (default) | `#,##0.00` | `Money` | the canonical picture; `PositiveMoney` inherits it |
| `money_de` | `#,##0.00`, `,` and `.` | `Money` | one picture, other separators (§5.1.1) |
| `money_ledger` | `#,##0.00;(#,##0.00)` | `Money` | a negative form |
| `country_upper` | `X(2)U` | `CountryCode` | upper case, sound because the Type requires it (§6) |
| `text_30` | `X(30)` | `ShortText` | narrower than `max_length(80)` — the one deliberate finding, `INT402` |
| `rate_pct` | `0.0%` | `DiscountRate` | a percentage: one decimal shown, three allowed, sound |
| `european` | `dd-MM-yyyy`, blank `—` | `Day` | a date picture and a blank |
| `yes_no` | `Yes;No` | `YesNo` | a boolean picture |

It carries exactly the three findings of §4 plus `INT402`, and no `INT202`: every
other pairing reads back every value its Type admits.

## 9. `sales_broken.json`

The same model with two of §5's mutations built in, so the case that matters
most to a user — a Schema that will not export, and what to do about it — is a
file rather than a paragraph:

- `Customer` is removed from `sales_schema`: `MOD503` (not closed) and `MOD509`
  (the cross-entity path leaves the schema), offering *Add the missing
  referenced entity* and *Add Customer to the schema*.
- `OrderLine.line_total` is overridden with `ShortText` instead of
  `PositiveMoney`: `MOD413`, offering *Choose a Type that narrows Money*. With
  the override changed, nothing references `PositiveMoney` any more, so a second
  `MOD601` joins the one for `Weight`.

`sales_schema` is blocked by exactly those three, each with a **Fix** in the
findings window; `support_schema`, which reaches none of it, still exports.
`test_the_broken_example_is_blocked_by_what_it_is_built_to_show` holds it to
that.
